# Zombie Shooter — Tier 1

Tier 1 is the full MVP scope from the reconciled plan: 1–4 player co-op, 3
zombie types (10 now), 3 weapons, endless waves with a boss every 10, coins + 10-level weapon upgrades,
DataStore persistence, and a lobby → match → lobby loop. It's built directly
on top of the Tier 0 prototype (see `zombie-shooter-mvp-plan.md`).

---

| Weapon model | `ReplicatedStorage/Shared/WeaponModelFactory.lua` | `CreateTool(weaponName)` loads the real model from Roblox's official [Weapons Kit](https://create.roblox.com/docs/resources/weapons-kit) per weapon (Pistol `118912302094201`, AssaultRifle (Auto Rifle) `96131146947811`, Shotgun `104068096273092`) via `AssetService:LoadAssetAsync` (requires "Allow Loading Third Party Assets" — see Setup below). None of the kit's own `WeaponsSystem` framework (fire/reload/ammo/recoil/camera/GUI scripts) is imported — only the visual geometry, using the kit's documented `TipAttachment`/`HandleAttachment` to correctly place the `Muzzle` attachment and derive `Tool.Grip`. Also adds a `LeftGrip` attachment on the Handle (heuristic placement — no such attachment is documented by the kit) as the off-hand IKControl's target, see `WeaponViewController` below. Falls back to a placeholder Tool (Handle + Muzzle + LeftGrip attachments) if the asset can't load or has no usable Tool/Handle inside. **`Tool.Grip` rotation fix:** the straightforward "invert `HandleAttachment`'s local offset" math produced a weapon visibly pointing the wrong way in-game. Debug logging (`ReplicatedStorage/Shared/CFrameDebug.lua`, invoked from `WeaponViewController`) comparing the actually-equipped `Handle`'s world orientation to `RightHand`'s showed an exact, fixed rotation error, identical across all three weapons. A first correction cancelled that out and confirmed (by reading `Tool.Grip` back) that its rotation really was identity afterward — yet the equipped `Handle` was *still* misaligned, this time by a different, equally exact 180°-about-Right flip. Conclusion: Roblox's real tool-equip pipeline applies some fixed offset of its own on top of `Grip` that isn't visible from the `Grip` property alone (most likely a built-in "how a fist grips a hilt" convention baked into the rig's own grip attachment) — the first fix addressed the asset-side math but not this deeper, always-present engine-side offset. `HANDLE_ATTACHMENT_ROTATION_CORRECTION` was recomputed to cancel *that* measured result instead (derived from the logged numbers both times, not guessed, cross-checked two independent ways) so the barrel ends up pointing wherever the hand points. |

| Zombie spawn + AI | `ServerScriptService/Services/ZombieService.lua` | ModuleScript now (Tier 0's endless auto-spawn loop is gone) — `SpawnZombie(type, position, hpMultiplier?, speedMultiplier?, damageMultiplier?)` is called by WaveService (multipliers come from the current wave's modifier). Every Melee/Ranged type now shares a unified `runChaseAI` using real `PathfindingService` routing (previously only Tank/Boss did — "keep server cost down" no longer held once the loaded subway map's real multi-level geometry made a straight-line `MoveTo` unable to navigate walls/stairs/ladders at all, which is what was causing zombies to visibly get stuck; extracted into a shared `moveTowardWithPathfinding` helper with a periodic-recompute + stuck-watchdog pattern, jittered per-zombie so many recomputing at once doesn't spike server load), plus a one-shot detonate-on-contact-or-death branch for Exploder (shares the same movement helper). **Fixed real bug:** `ApplyHitKnockback`'s brief `Humanoid.PlatformStand` toggle (needed so the knockback impulse is actually visible against the AI's own constant `MoveTo` calls) used to capture/restore a per-call snapshot — overlapping hits within the same ~0.15s window (e.g. one Shotgun blast's 8 pellets) could race each other into a state where the *last* callback to fire set `PlatformStand` back to `true` instead of `false`, permanently freezing the zombie's movement — exactly the reported "zombies get stuck after being hit." Fixed with one shared "stun expiry" clock per zombie that hits only ever extend, never independently restore from. **Fixed spawn distribution:** zombie spawn points used to be a purely geometric ring around the arena's overall bounding-box center — fine for the old flat open-box procedural arena, but for the subway map's real multi-level geometry most of those points landed inside walls or in unreachable voids, leaving only a handful of valid spots (reads as "zombies only spawn from one place"). Now built by `buildGeometryAwareSpawnPositions` in `MapBootstrap.server.lua`: samples a grid across the map's actual footprint, raycasts down to find real floor surfaces, rejects spots without enough headroom (wedged under a train/stairs/pipe), and greedily spreads the selected points apart — falling back to the old ring formula only if that search somehow finds nothing. **Probe height matters:** rays start only ~12 studs above the known play-level floor, *not* above the whole model's bounding box. A first version did the latter and took the first downward hit, which on an enclosed map like the subway station is its **roof** — so every spawn point landed on the roof. Zombies spawned fine but were invisible and unreachable, and once `MaxConcurrentZombies` filled with roof-stuck zombies `WaveService` blocked all further spawning, which in-game was indistinguishable from "zombies never spawn." **Reachability-validated:** each candidate floor position is then checked with an actual `PathfindingService:ComputeAsync` to the player spawn (using the same agent dimensions `ZombieService` uses at runtime), keeping only points a zombie can genuinely route from. Real floor with real headroom still isn't enough on this map — the track bed, the train interior, and areas behind barriers are all valid standing surfaces that are simply disconnected from the play area, and a zombie spawned there never reaches anyone, never dies, and **stalls the entire wave** (a wave only advances once the arena is clear). A startup `print` reports the spawn count and the spawn Y range against the arena floor Y so these regressions are immediately visible in Output if they recur. Complementing that at runtime, `ZombieService`'s pathfinding helper tracks continuous no-progress time and, after ~12s, teleports a genuinely stranded zombie back to a known-good spawn point (`rescueStrandedZombie`) — a zombie can still end up unreachable mid-match despite validated spawns, e.g. knocked off a ledge by the hit-knockback impulse or wedged between props, and a blunt-but-self-correcting teleport is strictly better than a match that can never progress. Each type loads a real toolbox model via `AssetService:LoadAssetAsync` (requires "Allow Loading Third Party Assets" — see Setup below) (Normal `3924238625`, Fast `306542926` "Skeleton Dog", Tank `305897868` "NERF Zombie", Boss `319386664` "Axe Monster"; Ranged/Exploder use the placeholder rig, no asset assigned yet), cloned per spawn from a cached template; any `Script`/`LocalScript` in the asset is stripped, *except* `Animate`/`RbxNpcSounds` on the Normal zombie specifically — the only asset verified to actually be a standard, compatible rig; every other (community-sourced) type always strips its own scripts too, since they'd otherwise risk hanging forever `WaitForChild`-ing body parts a non-standard model doesn't have (we drive HP/AI ourselves regardless — the asset's own AI is never trusted either way). The root part is standardized to `HumanoidRootPart` regardless of the source asset's naming. Falls back to the placeholder rig per-type if that type's asset can't load or has no usable Humanoid-capable structure (a warning prints either way, gameplay still works) — this placeholder is a full torso+head+2 arms+2 legs blocky R6-proportioned body: arms are welded in a fixed "reach forward" zombie pose, and legs are Motor6D-jointed at the hip and procedurally swing through a walk/run cycle (`animateLegWalk`) driven by actual root-part travel distance, snapping back to standing the instant it stops moving. Applies a knockback velocity impulse + a death groan sound ([community SFX](https://create.roblox.com/store/asset/116391542832455/Fast-Zombie-Die), used for every type) on every death, and a shorter, briefly-stunning knockback punch (`ApplyHitKnockback`) on every hit the zombie survives. |

| Client weapon holding (IKControl) | `StarterPlayer/StarterPlayerScripts/Controllers/WeaponViewController.lua` + `ReplicatedStorage/Shared/WeaponIK.lua` | Rebuilt per `Roblox Weapons Kit — Stable Weapon Holding & Shooting Implementation Guide.md`, replacing an earlier approach that directly overwrote the equipped weapon's `RightGrip`/`LeftGrip` `Weld.C0` every frame to cancel out the hand's own animated motion — that worked but fought Roblox's animation system by design. Two `IKControl`s are created per equip: a **right-hand** one (`ChainRoot`=upper arm, `EndEffector`=hand) that pulls the hand toward a small invisible attachment this script repositions every frame to track camera pitch/position, and a **left/support-hand** one that pulls the other hand toward the weapon's own `LeftGrip` attachment directly, requiring zero per-frame script work since IK continuously re-reads that attachment's live (moving) position on its own. This is the first time any weapon in this game has *any* left-hand interaction at all — Roblox's automatic Tool-equip only ever creates a right-hand grip Weld. Neither `IKControl` ever touches `Tool.Grip` or its frozen equip-time Weld (an earlier, unrelated attempt tried exactly that and — per this project's own history — produced correctly-computed values with zero visible effect, since Roblox only reads `Grip` once at equip; see `WeaponIK.lua`'s header for the full explanation of why this is a fundamentally different, unaffected mechanism). Both `IKControl`s use `Type = Position`, **not** `Transform` — an earlier pass used `Transform` (matching the guide's own example, forcing the hand's full rotation to match a computed world orientation) and it produced a visibly upside-down/broken-looking weapon plus shake while walking/sprinting. Root cause: `Transform` demands knowing exactly how `RightHand`'s local axes relate to a natural gripping pose, an undocumented per-rig detail — real Roblox developers building this same aim-IK pattern report needing to hand-tune a compensating rotation empirically with live visual feedback in Studio (no universal constant exists), and a subtly-wrong/unreachable rotation target recomputed every frame while the walk animation simultaneously fights for the same joint is a very plausible source of the shake. `Position` mode only has to reach a nearby point in space — no rotation guesswork, so there's no "impossible pose" to fight each frame. The tradeoff: the gun's barrel no longer visibly tilts to track camera pitch, only its position nudges a little; precisely re-adding pitch tilt would need the same kind of Studio visual tuning those developers describe, which isn't possible from code alone. Supports both R15 (two-segment arm, real elbow bend) and R6 (single rigid arm, shoulder-only) rigs; silently does nothing beyond the default equip pose if neither shape is found. Also proactively checks for a Tool already equipped the moment the character loads (not just future `Tool.Equipped` events), since the starting weapon is often already in the character's hand before this script finishes connecting. During reload, the left-hand IK disables (guide: "left hand releases grip → reload animation → left hand returns → IK enabled") while the right-hand aim target's *position* (not rotation) dips/returns via a tween. **Not implemented** (needs Roblox Studio's Animation Editor, a GUI-only workflow): the guide's separate `RifleHold`/`RifleWalk`/`RifleSprint` authored animations — this game also has no player sprint mechanic to distinguish. Local-only, same limitation as everything else client-side here. Third-person's held-position target (`GUN_OFFSET_THIRD_PERSON` + `getStabilizedCameraRotation`) was retuned after live testing showed the gun sitting down near the character's hip with the arm still in its plain idle pose: the original small/downward offset landed close enough to a naturally-hanging hand's resting position that the `Position`-type IK barely had to move it, and letting the target's height fully follow camera pitch made it dip even further whenever the (elevated, typically downward-angled) third-person camera looked down at zombies. Fixed by pushing the offset further right/forward and slightly *up* instead of down, and by making third person's target yaw-follow the camera but ignore pitch entirely (first person is unaffected — it still tracks full pitch, behaving like a viewmodel). **The barrel's own angle was still wrong after the position fix** (pointing at the floor) — root cause: Roblox's `RightUpperArm`→`RightHand` IK chain spans three full 3-DoF `Motor6D`s (shoulder/elbow/wrist), 9 rotational degrees of freedom for a single 3-DoF position target, so which way the barrel ends up pointing was an uncontrolled side effect of whatever bend the solver happened to pick — confirmed by diagnostics (`Muzzle`'s world orientation is consistently `Handle`'s rotated 180° about its own Up axis, and `Handle`'s now exactly equals `RightHand`'s, but neither tracks the camera's look direction). A second attempt switched the right-hand `IKControl` to `Type = Transform` to directly command that rotation (feasible now that `Tool.Grip`'s own rotation nets to identity — see the weapon model note below); live testing disproved it — the commanded and actual rotations diverged by tens of degrees every frame and the walking shake came back, confirming (per Roblox's own DevForum reports) that this really needs physics constraints (`HingeConstraint`/`BallSocketConstraint`) added to the rig in Studio to converge reliably, which a script alone can't set up. **Current state**: reverted to `Position` mode for both hands (stable, zero shake, correct reach position, barrel angle uncontrolled) — plus a new opt-in mechanism to sidestep the problem entirely per weapon: `WeaponConfig[weaponName].HoldAnimationId` — if set to a published Animation asset id, `WeaponViewController` loads+plays it at `Enum.AnimationPriority.Action` (looped) instead of creating **either** hand's `IKControl` for that weapon, so an authored Studio pose (Animation Editor, GUI-only) fully overrides the walk cycle's arm swing for whichever joints it keyframes with zero live IK solving — the standard, reliable way most Roblox FPS/TPS games actually solve this. ### Controls

- **Fire:** hold left mouse (desktop) or hold your finger down on the screen (mobile/touch)
- **Reload:** press `R` (desktop) or tap the **RELOAD** button
- **Switch weapon:** press `1`/`2`/`3` or click a slot in the on-screen weapon hotbar (bottom-center — only shows weapons you've unlocked)
- **Toggle first-person / third-person:** press `V` or tap the on-screen `VIEW (V)` button
- **Perks shop:** press `P` or tap `PERKS (P)` (empty until Game Pass IDs are configured — see the Robux perks row above)
- **Open upgrade panel:** press `U` or tap the **UPGRADES** tab (works anywhere, no stall needed)
- **Open leaderboard:** press `L` or tap the **LEADERBOARD** tab
- **Revive a downed teammate:** walk up to them and hold `E`
- **Buy a weapon / interact:** walk up to a stall and hold the interact key (`E` by default)
- **Start a match:** walk up to one of the 4 glowing portals in the lobby and hold `E`, then pick a party size (1-4). You're teleported inside the portal to wait. Solo starts after a short 5s countdown; 2-4 waits up to 20s for others (or starts early once full).
- **Join someone's match:** hold `E` on the portal they're waiting in — that joins the party and teleports you inside too. The portal shows a live "2 / 4 joined" count above it.
- **Leave a party:** press **EXIT PORTAL** on the waiting panel. The portal is walled off, so this button is the only way back out.

## Setup

1. Install [Rojo](https://rojo.space/) (VS Code extension + the `rojo` CLI) if you haven't already.
2. From this folder, run:
   ```bash
   rojo serve
   ```
3. In Roblox Studio, open the Rojo plugin and click **Connect**.
4. Press **Play** (Studio Play, not just Run).
5. You spawn in the **lobby**. Nothing starts automatically — walk onto a portal, pick a party size, and the countdown into wave 1 begins.

**Studio setup — 2 separate settings, both under *File → Game Settings → Security*:**

- **Enable Studio Access to API Services** — needed for `DataService`'s DataStore calls (coins/unlocks persistence). Without it, DataService falls back to in-memory defaults each session.
- **Allow Loading Third Party Assets** — needed for `ZombieService`/`WeaponModelFactory` to load *any* of the real weapon/zombie models. None of those assets are owned by your account or by Roblox, so `AssetService:LoadAssetAsync` refuses to load them at all until this is turned on — **this is almost certainly why you're only seeing placeholder rigs/blocks.** Without it, every weapon/zombie falls back to its placeholder (a `WeaponModelFactory:`/`ZombieService:` warning prints in the Output window either way — check there if something still won't load after enabling this).

Both settings are saved with the place, so you only need to set them once (per place file).

**Real asset caveat:** Normal's zombie model and all 3 weapon models are official Roblox kits with documented structure (NPC kit / Weapons Kit), so their loading is fairly precise. The Fast/Tank/Boss zombie models are still unofficial toolbox uploads of unknown internal structure — `ZombieService` handles them defensively (strip unknown scripts, guess at root parts), but grips, scale, or collision may need manual tuning in Studio once you've seen them in-game.

**If you still only see placeholders after enabling "Allow Loading Third Party Assets":** open the Output window in Studio and look for lines starting with `WeaponModelFactory:` or `ZombieService:` — each one states exactly why that specific asset fell back (load failure vs. no usable Tool/Handle/Humanoid found inside it, or a `:Clone()` failure — some Store assets come back with `Archivable = false` on parts, which both scripts now force back to `true` on the cached template right after loading it), which is the fastest way to tell what's actually wrong.
